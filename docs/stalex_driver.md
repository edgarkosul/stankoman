# Паспорт контекста: драйвер импорта фотогалереи из YML-фида Stalex

> Документ-хэндофф для AI-агента-реализатора (Claude в VSCode / Claude Code).
> Цель — дать всё, что нужно для реализации, без повторного ресёрча фида.

---

## 1. Задача в одном абзаце

Штатный YML-парсер проекта берёт изображения товаров **только** из стандартного тега `<picture>`.
У поставщика **Stalex** в `<picture>` лежит лишь одно (главное) фото, а вся остальная галерея
вынесена в **нестандартный** `<param>`. Нужно написать **специфичный для этого поставщика драйвер**,
который дочитывает галерею из этого параметра и передаёт её в существующий конвейер импорта картинок.
Работа для клиента — платная доработка.

## 2. Фиды поставщика

| Роль | URL | Картинки |
|------|-----|----------|
| YML с характеристиками (**рабочий для галереи**) | `https://www.stalex.ru/bitrix/catalog_export/yandex_498907.php` | `<picture>` = 1 главное фото + галерея в `<param>` |
| Обычный YML | `http://www.stalex.ru/bitrix/catalog_export/yandex_4659718.php` | только `<picture>` = 1 фото, галереи нет |
| Excel | `http://stalex.ru/upload/CSProductExport.xlsx` | не анализировался (бинарный, нет доступа) |

**Вывод:** для галереи использовать только фид `yandex_498907.php`. В обычном YML доп. фото
физически отсутствуют — драйвер там ничего не даст.

## 3. Ключевой факт: где лежит галерея

Дополнительные изображения — в отдельном параметре, значение = список URL **через `, ` (запятая + пробел)**.
Имя параметра по данным клиента — **`Фотогалерея`** (в самом фиде имя в кодировке windows-1251).

Пример элемента (формат):

```xml
<param name="Фотогалерея">https://www.stalex.ru/upload/iblock/dc3/3uw3e1g0ibqkcybqq4n0kfuc7ufn5wuk.jpg, https://www.stalex.ru/upload/iblock/ad0/2w3kzgb9n6iv1x4gcd1oc3lx8guuk7hj.jpg, https://www.stalex.ru/upload/iblock/fb4/tk20i7spdtsm1hbwa10aaj8lkut76zjg.jpg</param>
```

## 4. Что должен делать драйвер (specifics)

Специфичная логика минимальна — фактически «найти параметр и порезать строку». Всё, что после
(скачивание, дедуп, привязка к товару, раскладка по полям/структурам проекта), — это **уже существующий
общий конвейер импорта картинок**, одинаковый для любого источника. Не переписывать его — только подать в него URL'ы.

Алгоритм для одного `<offer>`:

1. **Кодировка.** Читать фид как **windows-1251**, а не UTF-8. Иначе имя параметра не совпадёт.
2. **Найти параметр** галереи по имени `Фотогалерея` (сверить точное имя после декодирования cp1251 — см. §6).
3. **Если параметр пустой или отсутствует** — галереи нет (нормальная ситуация, напр. офферы `39`, `84`). Ограничиться главным фото из `<picture>`, идти дальше.
4. **Split по `,`**, затем **`trim()`** каждого элемента (разделитель `, ` — без trim получите ведущий пробел в URL).
5. **URL оставлять как есть**, включая `%20` (пробел в имени файла, напр. `DSC08350%20bl.jpg`). Не «чинить», не декодировать.
6. **Собрать итоговый список фото товара** = `<picture>` (главное) + элементы галереи.
7. **Дедуп.** Главное фото из `<picture>` может **дублироваться** в галерее под **другим путём/хешем**
   (тот же файл, другой URL). Дедупить **по имени файла** (последний сегмент пути), а не по полному URL.
   Пример: оффер `70` (3-IN-1) — `<picture>` = `.../66b/.../DSC08350 bl.jpg`, первый в галерее = `.../ac7/.../DSC08350 bl.jpg`.
8. **Определить «главное».** Решить product-политику: `<picture>` — это отдельная главная картинка,
   а галерея — дополнительные; либо `<picture>` = первый кадр галереи. По умолчанию: `<picture>` главная, галерея после неё (с дедупом из п.7).
9. Передать финальный упорядоченный список в существующий импорт-пайплайн.

## 5. Прочие нестандартности фида (знать, не обязательно обрабатывать)

Галерея — **не единственное** отклонение от стандартного YML. По результатам осмотра фида:

- **Кодировка windows-1251** (не UTF-8). Формально YML допускает, но стандартные парсеры на UTF-8 спотыкаются на именах параметров.
- **Нестандартный тег `<characteristics>`** с CDATA — HTML-дамп характеристик (`<br />`-простыня), дублирует данные из `<param>`. В стандартном YML такого элемента нет; штатный парсер его игнорирует. Для задачи по картинкам — не нужен.
- **Мусор в `<description>`**: незакрытые CMS-плейсхолдеры `#BLOCK_1#`, `#BLOCK_2#`, `#BLOCK_SLIDER_1#` прямо в тексте. Если проект тянет описания — чистить отдельно (вне рамок этой задачи).
- **Балласт из пустых `<param>`**: у каждого оффера ~150 параметров, большинство пустые. Парсер должен спокойно переваривать пустые значения.
- Семантика характеристик — supplier-specific (какой param что значит). Маппинг руками, но это обычная работа, а не «нестандарт». Вне рамок задачи по картинкам.

## 6. Открытые вопросы / проверить перед реализацией

- [ ] **Точное имя параметра галереи** в cp1251. Клиент называет `Фотогалерея`; подтвердить, декодировав фид из windows-1251 (в сыром виде имя выглядит как «кракозябры»). Возможны вариации написания.
- [ ] **Полный прогон по всему каталогу.** Осмотрены только первые ~10 офферов (выгрузка длинная). Прогнать скрипт, собирающий **все уникальные имена `<param>`** и типы значений, чтобы убедиться, что галерея — единственный «нестандарт с данными в неожиданном месте» (нет ли видео, документов, второго набора картинок и т.п.).
- [ ] **Политика главного фото** (§4 п.8) — согласовать с продуктовой стороной.
- [ ] Стабильность имени параметра между обновлениями фида (не завязываться на порядок `<param>`, только на имя).

---

## 7. Definition of Done

- Для товаров с непустой `Фотогалерея` в проект импортируется вся галерея (главное + доп.), без дублей.
- Для товаров с пустой/отсутствующей галереей поведение не меняется (только главное фото).
- Драйвер устойчив к cp1251, пробелам-разделителям, `%20` в URL и пустым параметрам.
- Логика изолирована как отдельный драйвер под Stalex, штатный YML-парсер не затронут.
- Существующий конвейер скачивания/раскладки картинок переиспользован, не продублирован.
